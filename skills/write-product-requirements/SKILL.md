# Write Product Requirements

## Contract

Requirements establish a shared product contract, not a retrospective justification for a chosen solution. Ground claims in evidence, keep outcome separate from implementation, and expose unresolved decisions.

## Workflow

1. Read existing strategy, jobs, research, decisions, system constraints, and neighboring specs before asking for missing context.
2. Define the problem, affected segment, situation, evidence, and consequence.
3. State desired outcomes, success evidence, and strategic contribution.
4. Describe the user journey or scenarios and write prioritized, testable product behavior.
5. Define quality attributes and constraints: accessibility, privacy, trust, reliability, performance, compatibility, compliance, and operations as relevant.
6. State non-goals, dependencies, assumptions, risks, rollout, measurement, and unresolved questions.
7. Link evidence and decisions. Mark facts, hypotheses, commitments, and proposals distinctly.
8. Review for altitude, contradictions, ambiguity, solution leakage, and verifiability.

## BuildBetter Acceleration

If BuildBetter MCP is available, search organization skills first. Use calls, signals, surveys, documents, knowledge pages, projects, triage, and linked tickets to ground the problem and avoid duplicate work. Mutating project state still requires explicit approval.

## Output

Return a concise requirements document plus an evidence ledger, open-decision list, assumption register, and acceptance or outcome scenarios.

## Quality Gate

Every requirement must be necessary, comprehensible, and verifiable. Remove unsupported urgency, feature requests presented as needs, implementation details that belong in design, and hidden non-goals.
